# 兼容约束的演进

用于说明信息和决定如何变化的假设案例，不描述任何真实接口或迁移进展。

## 场景

服务内部的调用方 A、B 正在从旧接口迁到新接口。项目要求迁移期间保持其功能可用。agent 被授权修改内部实现，但发布、公共接口承诺的改变需要另行授权。

当前代码含旧接口适配层，当前规格写明：“在 A、B 完成迁移前，保留旧适配层，避免调用失败。”活动任务记录各调用方的迁移工作。引入适配层的 commit 保存当时为何选择适配层而非一次迁完的理由。

## 条件发生变化

| 获得的信息 | 能得出的判断 | 可以推进的工作 |
|---|---|---|
| 源码中 A、B 已使用新接口 | 已知源码中的调用已迁移 | 查部署、回退路径和其他依赖，不直接宣布可移除 |
| 只有一段时间内没有旧接口流量 | 观察范围内未发现调用 | 判断是否覆盖低频任务及相关环境 |
| A、B 的相关部署已迁移，回退版本也兼容新接口，接口仅供这两者使用 | 在这些假设成立的范围内，原兼容条件已解除 | 重新选择保留或移除，并检查行动权限 |
| 发现还有未知的外部调用方 | 原范围假设不成立 | 保留现状、明确影响，提交所需产品或兼容决策 |

这些信息不是固定的强制检查清单。应围绕具体系统的依赖、承诺与变化成本决定需要知道什么。

## 作出选择

假设相关范围已清楚，适配层也没有其他保留理由，agent 推荐移除它以减少重复维护。若移除属于已授权的内部实现调整，可以准备代码和文档变更；若影响对外承诺或需要发布，按该边界取得授权。

人参与的议题应是具体取舍，例如“是否结束对仍有用户使用的旧客户端的支持”，而不是每次修改文档都要求审批。

## 信息如何落位

| 载体 | 移除前 | 有效决定落实后 |
|---|---|---|
| 当前代码 | 新接口与旧适配层 | 移除旧适配层后的实现 |
| 当前规格 | 新接口行为及兼容条件 | 当前接口行为；仍适用的版本范围明确列出 |
| 活动任务 | A、B 的迁移和剩余工作 | 关闭已完成事项，只保留实际待办 |
| Git 历史 | 引入兼容层的资产状态与理由 | 增加移除的状态与必要依据，保留原历史 |
| 发布记录与运行状态 | 原部署 | 发布发生后再记录实际生效状态 |

代码变更已经提交，不等于部署已经完成；规格也不能声称尚未发布的能力已经在线。

## 可迁移的设计原则

- 当前成果保留影响行动的适用条件，有助于后继 agent 识别何时需要重议。
- 历史帮助解释条件，不替代对当前状态的判断。
- 条件改变、决定改变、实现改变与对外生效可以发生在不同时间。
- 事件与当前状态分别维护，通过相关对象连接，不依靠同一文件积累全部过程。
