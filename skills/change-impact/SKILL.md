# 变更影响

把一项明确变化转为有依据的处理范围。目标是知道哪些对象需要怎样处理，而不是收集所有关键词命中或生成全仓知识图谱。

## 明确变化与请求

结合本轮目标、项目约定和相关差异，明确旧行为、新行为和适用边界；计划中的变化也可以分析，不要求先产生 diff。辨别无关的既有改动。若变化本身无法确定，询问具体缺失输入，不凭历史待办替用户选任务。

区分用户要求分析、制定计划还是实施。只分析时读取并在回复中给出结论，不修改项目、不默认新建影响报告；技能不扩大已有权限。

## 沿语义追踪依赖

从变化的入口沿生产者、转换层、消费者及反向依赖定位。按实际变化检查接口、持久化数据、配置、测试、当前说明和活动工作；利用项目已有类型检查、契约差异或依赖工具，不重复造工具。

追踪的不只是名称和类型，还包括单位、默认值、失败行为、顺序、生命周期及兼容承诺。相同类型可承载不同含义；包装器、别名、序列化和持久化可能隐藏间接消费者。每项影响应能解释“哪条依赖导致什么后果”，不能只凭同名或相邻就要求修改。

区分当前生效契约、版本化旧接口和历史记录。旧版本承诺可能要求兼容处理；历史示例不一定需要重写。源码中的意图、构建产物与实际部署状态分开判断。

## 收敛为处理范围

按对行动有用的粒度区分：

- 已确认影响：给出对象、依赖依据、后果与必要处理或检查。
- 待查影响：说明缺少的消费者、运行状态或范围信息，以及取得它的具体下一步。
- 容易误判但已排除的对象：必要时说明排除理由，不列全仓“不受影响清单”。

搜索无命中不能证明没有消费者，尤其涉及跨 repo 调用、动态加载、已有数据或外部使用者时。声明实际查到的边界，不把未知伪装成不受影响，也不因为未知而阻塞所有独立工作。

当足以决定本轮处理范围，或剩余范围受明确的信息／访问缺口限制时停止扩展。按请求给出简短分析、更新已有任务载体或执行已授权改动；不强制填写固定模板。不把影响清单等同于已实施、已测试或已迁移，最终交付仍需核对实际完成状态。
