# 工作分解

把明确目标转为可执行、可接续的任务图。分解依据是结果和依赖，不是文件数、阶段名称或可用 agent 数量；计划不自动授权委派、启动多个执行者或外部动作。

## 找到可独立交付的结果

读取相关目标、约束、当前工作区和完成条件。每个任务应有可判断的结果；“研究、写代码、测试”若没有对象与完成条件，不足以成为执行任务。小工作保持单任务，只有收益超过协调成本时才拆分。

优先按行为边界、稳定接口或可恢复的交付增量拆分。模块内部可独立选择的细节无需全员共享。若两个任务必须反复读取对方实现才能推进，考虑合并、先稳定契约或改边界，而不是增加交接文档。

## 表达真实依赖

为每项任务给出输入／前置条件、产出、相关约束、核对方式和需要的项目入口；执行者只获得完成任务必要的背景。引用权威材料，避免复制容易过期的全文。

有向边表示后项确实需要前项的结果，不用建议顺序冒充硬依赖。识别共享数据、接口、版本与工作区写入冲突；文本不冲突不代表语义独立。探查中发现循环时，将未知拆成有界调查或先确定共同契约，再调整任务图。

用适合规模的列表、依赖表或 DAG 表达，图与任务说明保持一致。关键任务说明失败／缺输入后怎么办；不强制所有任务都有相同模板。

## 安排整合与下一步

明确谁负责共享契约、谁维护什么结果、谁整合并核对端到端行为。计划中的执行者身份未指定时保留待分配，不假装已经委派；有授权且工具适用时才实际分派。共享工作区要有写入边界和协调方式。

沿用已有任务系统记录待做、进行、阻塞和完成；完成须有对应结果，不能按写了多少字或发出了任务判断。指出现在可启动的任务、真正阻塞的任务及具体缺口，不把所有工作都串行等待人确认。

任务足以被执行且整合责任清楚时停止细分；新依赖出现后更新受影响部分，不为每个命令建立节点。只要求计划时到可执行任务图为止，不自行实施。
