# 上下文边界

针对反复出现的知识与协调负担，找到系统边界问题并推荐一项有依据的改进。目标是减少完成工作所需的共享认识，同时保留正确性与可维护性；少读文件本身不是唯一目标。

## 识别重复负担

从实际变更、依赖、评审／交接及必要历史中找出：哪些知识每次都必须重新解释、哪些局部变化总要跨模块同步、哪些错误由共同含义不清导致。不要因一次搜索很多文件或一个大文件就诊断架构有问题。

区分材料难发现、当前规则过期、任务划分不清和真实语义耦合。入口索引或修正一处契约足以解决时不重构；更多摘要也可能只是掩盖模块必须共享过多内部知识。

## 追踪必须共享的决定

沿重复变更追踪数据、接口、共享状态、单位、配置和责任归属，明确外部参与者必须知道什么、哪些内部选择本应被隐藏。将必要业务耦合与偶然实现耦合分开，避免用再包一层接口把依赖改名隐藏。

比较维持现状、澄清契约／入口、移动职责或调整模块边界的实际代价。优先一项可逆、可局部试用的变化，说明预计减少哪种具体协调、代价是什么，以及怎样核对有没有把负担转移给别处。

## 给出有范围的调整

推荐中说明新边界、稳定契约、内部可独立变化的部分、迁移与回退限制，以及共享语义由谁或哪个模块维护。无法从材料确认重复模式时，明确证据不足并提出最小观察，不编造收益或立即重写仓库。

只要求分析时不修改代码／项目结构；获得实施授权时保护既有工作，按局部增量调整并检查跨边界行为，不借机会全面重构。沿用项目载体保留有效约束与必要理由，不默认新增全局规则、强制 hooks 或第二套知识库。

找到足以解释重复成本的具体边界并形成可执行建议，或已有明确证据缺口时结束；实际协调成本是否下降需要后续使用观察，不能从文件数减少推断。
